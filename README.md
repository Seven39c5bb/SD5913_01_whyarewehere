# Why Are We Here?

> **Working thesis / 核心论点：** 作为一名设计师或艺术家，我学习编程，并不是为了在写代码的速度上与 AI 竞争，而是为了理解数字媒介、把模糊意图转化为可判断的规则，并对最终作品保持批判性与作者责任。
>
> **写作提醒：** 最终正文应为 **500–1000 words**。下面建议以约 **750–850 words** 为目标；完成初稿后删除所有方括号提示。

## 1. The Uncomfortable Question（约 80–100 words）

[用一个具体场景开篇：例如，你曾用生成式 AI、创意编程工具或一句 prompt 尝试做某件作品。描述它很快产出了“能用”的结果，但这个结果在哪一点上不是你真正想要的。]

[紧接着提出矛盾：既然机器已经可以把自然语言变成代码，我为什么还要学习编程？避免泛泛讨论“科技发展很快”，把问题放回你自己的设计／艺术实践。]

**Section claim:** [一句话说明这个例子暴露了什么问题，并自然引出全文论点。]

## 2. From Description to Specification（约 150–180 words）

[分析“描述”与“指定规则”的差别。比如，“做一张令人不安的生成海报”只是描述；颜色如何变化、元素如何重复、随机性如何受限，才是可执行的 specification。]

[展开你自己的例子：]

- [你最初想实现什么？]
- [AI／软件第一次给了你什么？]
- [结果具体错在哪里，而不是只说“不够好”？]
- [如果你懂变量、条件、循环、随机性或参数，你会怎样修改规则？]

**Section claim:** [编程知识如何让你把审美判断转化为可以测试和调整的决定？]

## 3. Reading Code Is a Form of Judgement（约 130–160 words）

[承认 AI 写代码的现实：未来大量代码可能并非由你逐字输入。然后区分“生成代码”和“判断代码”。]

[说明设计师要判断哪些东西：代码是否真的实现意图、是否稳定、是否包含偏差、是否过度复杂、修改后会造成什么后果。继续沿用同一个个人案例，避免另起一个泛泛的技术话题。]

[可加入一个反方观点：如果 AI 的结果已经足够好，学习语法是否只是浪费时间？随后回应：你认为哪些基础仍然需要亲自理解，哪些操作则可以放心交给 AI？]

**Section claim:** [你的价值不只在“写”，还在于能否读、质疑、选择和负责。]

## 4. Code as Material, Not Just a Tool（约 130–160 words）

[把代码与设计材料联系起来：画家理解颜料，摄影师理解光；数字创作者若不了解代码，会看不见哪些可能性？]

[联系课堂中 Don Ihde 的 mediated perception，或 Dylan Beattie 的 *The Art of Code*。不要只复述材料，要明确赞同、修正或反对其中一个观点，并把它带回你的实践。]

[给出一个具体的媒介限制或可能性，例如随机数、实时输入、递归、数据结构或浏览器交互如何改变你能想象的作品，而不仅是帮助你更快完成既定构想。]

**Section claim:** [理解媒介如何改变“我能做什么”以及“我会想到什么”。]

## 5. Authorship After Automation（约 120–150 words）

[讨论使用 AI 后的作者身份。不要只问“作品是谁的”，而要提出你自己的判断标准，例如：谁定义目标、谁选择规则、谁识别失败、谁承担结果。]

[诚实划定边界：在你的工作流程里，哪些部分可以委托给 AI？哪些关键决定不能委托？理解系统运作是否会改变你对作者身份的判断？]

**Section claim:** [作者性不一定来自逐字写完所有代码，而来自有能力作出并解释关键决定。]

## 6. What I Am Here to Learn（约 90–120 words）

[回到标题并直接回答问题。不要总结成“所以编程很重要”；列出 2–3 个对你个人实践明确而有限的目标。]

[可以采用这样的逻辑：我不需要证明人类永远比机器更会写代码；我需要学会把意图变成系统、理解系统如何塑造作品，并判断何时接受或拒绝机器的建议。]

**Closing sentence:** [用一句简洁、有立场的话结束，最好呼应开头的具体场景。]
